AI-四条建模路线：能力边界、显存代价与选型

#AI #游戏开发

这两年「AI 建模」被当成一个东西来讲，但真正落到项目里会发现，市面上叫这个名字的至少有四类完全不同的技术：让大模型写 Blender 脚本、从图或文字直接生成网格、从照片视频重建、以及参数化 CAD。

它们的差别不在模型参数量，而在于交付物到底是什么——是可编辑的建模意图，还是一堆三角面。这个差别几乎决定了后续 80% 的成本：三角面能看不能用，改尺寸要重做，做动画要重拓扑；而可编辑的意图改一个参数就重跑一遍。

本文按这四条路线拆开讲，重点记录每条路线的能力边界、实际踩过的坑，以及按任务反查该用哪条。文中模型参数、显存与版本号来自各项目官方仓库和产品页（抓取于 2026 年 10 月）；带「判断」字样的内容是我的主观结论，不是官方说法。

1. 四条路线，按交付物划分

先给一张全景图。划分依据是产物形态，不是模型规模——这比参数量更能预测后续成本。

路线 交付物 一句话定位
A 代码驱动 可重跑的 Python 脚本、参数化场景 把建模变成代码，胜在批量与可复现
B 生成式 三角网格 + PBR 贴图 从图/文直接出形面，胜在速度与形面自由
C 重建式 高斯球、网格、场景 从真实素材恢复，胜在真实感与可度量
D 参数化 CAD 带特征树的 B-Rep 实体 生成的是特征与约束，胜在可制造

图 1　四条路线按「产物形态」划分。参数量相同的两个模型，如果交付物一个是有语义的脚本、一个是三角面汤，它们在管线里的位置完全不同。

四条结论先放在这里：

  1. 没有任何一条路线能直接产出「布线干净、UV 规整、可蒙皮」的成品角色。 这是当前所有方案共同的上限，不是某一个模型的短板。
  2. 路线 A 在生产环境里被严重低估了。 它的价值不在「AI 会建模」，而在于把一次性的手工劳动变成可版本管理、可批量重跑、可参数化的资产。
  3. 路线 B 已经能用于实际生产，但只适用于「外观资产」这一档——背景道具、概念可视化、风格化小物件。需要精确尺寸或二次编辑的主角资产，仍然要回到手工或 A/D。
  4. 最现实的组合是 A + B：A 搭骨架与批量规则，B 出形面与贴图，人工做重拓扑与绑定。

2. 这四年到底变了什么

理解现状需要一条主线：技术演进的方向，是控制权逐步从模型回到人手里。

  • 2022–2023：用 2D 监督 3D。 DreamFusion 一类方法借 2D 扩散模型的先验「雕刻」三维形状，耗时几十分钟到小时级，产出是「概念上像」，细节和材质基本不可用。
  • 2024：前馈式三维原生生成。 LRM、TRELLIS 这类工作让模型直接从图像回归三维表示，单卡几十秒出结果，成本降了一个数量级。这是真正的分水岭。
  • 2025 上半年：材质管线成熟。 混元 3D 2.1 引入 PBR 材质生成（反照率、粗糙度、金属度），TripoSG 用大规模整流流把形状质量推到可用水平，并且开源权重可以在本地跑。
  • 2025 下半年：分辨率、部件与条件控制。 TRELLIS.2 把体素分辨率推到 512³–1536³ 并支持开放表面与内部结构；混元 3D 系列走向部件级生成（P3-SAM + X-Part）与多模态条件控制（Omni：点云、体素、骨架、包围盒）。
  • 2026：产品分化。 商用平台（Meshy 7.1、Tripo、Rodin）不再拼「能不能生成」，而是拼绑定、动画、引擎集成与工作流嵌入。

图 2　四年里的关键节点。时间线只标技术路线节点，不构成各版本能力的精确排名。

「控制权回到人手里」具体指什么？早期模型只能「给一张图，出一个大概」；现在的模型可以接受包围盒、体素、点云、骨架作为条件——也就是说，可以先规定「这个物体占多大、是什么姿态」，再让模型填细节。这是从抽卡到可控生产的关键一步。

3. 路线 A：AI 写脚本驱动 DCC 建模

这条路线我自己用得最多，也最值得展开。

3.1 三种实现形态

同样是「让 AI 写建模脚本」，工程实现差别很大，能力边界也不同。

形态 做法 代表 特点
MCP 直连 AI 通过 socket 连到运行中的 Blender 实例，直接在其内部执行 bpy 代码 mcp-for-blender（原 blender-mcp） 能「看见」视口、能读场景、能迭代；反馈闭环最完整
纯代码生成 让模型一次性写出 .py，本地 blender -b 跑 任意 LLM 简单、可版本管理，但没有反馈，错了只能自己看报错
参数化脚本 用 CAD 内核的 Python API 生成可参数化实体 CADQuery、build123d 输出 STEP 等工程格式，可精确到尺寸

MCP 这条路目前的事实标准是 mcp-for-blender（原 blender-mcp，MIT）。它把能力收敛成九个工具，其中最关键的是三个：

  • execute_blender_code：在运行中的 Blender 里执行任意 Python，也就是真正干活的手；
  • look：多角度、相机、线框、X-ray、渲染帧的视觉回读，也就是真正的眼睛；
  • get_scene_info：场景结构与对象摘要，让模型知道「现在有什么」。

此外它还能直接调 Meshy、Tripo、Hyper3D Rodin、Hunyuan3D 这些生成模型并导入场景，以及从 Poly Haven、Sketchfab、Poly Pizza 拉现成资产。这意味着路线 A 和路线 B 在工具层面已经打通——同一个对话里可以先让模型生成一个道具，再用脚本把它复制 200 份摆成阵列。

图 3　MCP for Blender 的实际工作状态：左侧是 AI 对话，右侧是 Blender 视口，指令「Create wooden pyramid in Blender」执行后的结果直接可见。（来源：ahujasid/blender-mcp 官方仓库）

3.2 为什么它能工作

这条路线之所以有效，不是因为模型「懂建模」，而是因为把建模变成了一个带反馈的代码生成任务——而代码生成恰恰是大模型最擅长的。

图 4　五个阶段。真正的价值在最后两步：执行结果和视觉回读会被送回模型，形成闭环。

关键在于第 5 步。纯「一次生成」的方案失败率很高，因为模型不知道自己在三维空间里错在哪；一旦有了截图回读，模型就能自己发现「这个门开在墙外侧了」，然后修。这是 MCP 形态相对于「让 AI 写脚本我自己跑」的核心优势。

3.3 它擅长什么

判断依据是任务是否具备可被语言描述的结构。

  • 规则驱动的场景铺量：城市街区、货架陈列、停车场、栅栏、楼梯。这类任务本质是参数化，脚本天然擅长。
  • 参数化变体：一套脚本出 200 个尺寸不同的柜子、门、齿轮。改一个数字重跑，手工建模做不到。
  • 管线杂活：批量重命名、批量 UV 展开、批量权重传递、批量导出 FBX、按规范整理层级与命名。这些任务枯燥但规则明确，是当前性价比最高的落地场景。
  • 场景搭建与布局：按表格数据摆放物体、按路径撒点、按规则添加细节。

3.4 它不擅长什么

这一点必须说清楚，因为它决定了不该在这条路线上浪费时间的地方。

  • 单件高审美造型。 模型不理解「这里再收 2 厘米」的手感。它能把比例算对，但算不对好看。凡是需要审美判断的形面调整，仍然得手工。
  • 长脚本极度脆弱。 Blender 每半年一个大版本（4.5 LTS → 5.0 → 5.2 LTS），API 会变。一段 300 行的脚本跨版本失效是常态。脚本越短、依赖越少，生命力越长。
  • 拓扑质量取决于你给的建模范式，而不是模型。 如果脚本用布尔运算堆形状，出来的一定是烂拓扑；如果脚本用基元 + 阵列 + 修改器，出来的是干净的。是你在决定质量，AI 只是执行。

3.5 继续走这条路的几个实操要点

  1. 把建模范式写进系统提示。 明确要求优先用基元 + 修改器（Bevel、Array、Mirror、Solidify），禁止布尔堆叠；物体命名遵循项目规范；所有物体归入指定集合。这一条对产出质量的影响大于换模型。
  2. 强制要求视觉回读。 每次修改后让模型调 look 看一眼，而不是盲改。多轮迭代的质量差异很明显。
  3. 增量修改，不要重写。 让模型只改出错的那几行，而不是重新生成整段脚本。整段重写会把已经调好的部分一起弄坏。
  4. 脚本落地成文件。 把跑通的脚本存进项目仓库，配一份参数说明。这样它就变成了资产，而不是一次性对话产物。
  5. 注意安全边界。 execute_blender_code 能执行任意 Python，而 Blender 的 socket 服务器没有认证和加密。只绑定 localhost，不要在不可信网络里开；跑之前先存盘。

3.6 一个容易忽略的点

路线 A 的真正产出不是「模型」，而是一套可复用的生成规则。一旦把「这条街怎么建」沉淀成脚本，下次做同类场景的成本接近于零。

这是它与路线 B 的根本差异：路线 B 每次生成都是独立的一次抽卡，路线 A 是一次投入、长期复用。如果需求是重复的、有规律的，路线 A 的长期成本远低于路线 B。

4. 路线 B：生成式 3D 大模型

4.1 形状与材质是两个独立问题

几乎所有主流模型都把生成拆成两段：先出几何，再出材质。理解这一点，就能理解为什么经常遇到「形对但质感假」。

图 5　主流生成式 3D 的两阶段结构，以及形状中间表示的四种选择。中间表示的选择直接决定了成败与代价。

以混元 3D 2.1 为例，它是这个结构的典型样本：Hunyuan3D-Shape（3.3B）负责出无纹理网格，Hunyuan3D-Paint（2B）负责合成 PBR 材质。纹理阶段依赖多视角渲染与参考分支，这也是它显存开销远高于形状阶段的原因——形状 10GB，纹理 21GB，全流程 29GB。

图 6　上方是形状生成（DiT + VAE 解码），下方是纹理合成（多视角 + 参考分支）。（来源：Tencent-Hunyuan/Hunyuan3D-2.1 官方仓库）

4.2 开源模型：能本地跑的那一档

这一档最值得关心，因为它意味着无 API 成本、数据不出本地、可以集成进自有管线。

4.4 这条路线真正的短板

诚实地讲，生成式 3D 有四个绕不过去的问题：

  1. 布线不可控。 除了 Tripo Smart Mesh 这类专门方案，多数输出是三角面汤，UV 是自动展开的碎块。想直接进正式管线，几乎都要重拓扑。
  2. 拓扑一致性差。 同一个提示词生成两次，布线完全不同。这意味着无法做 blend shape、无法做规范蒙皮、无法做资产变体。
  3. 尺寸与比例不可靠。 生成的是「看起来对」的模型，不是「量起来对」的模型。需要真实尺寸的工业件、建筑构件必须回到路线 D。
  4. 部件语义丢失。 一个整体网格就是一块，没有「门」「窗」「轮子」的概念。要做动画就得先分割，而分割本身又会引入误差。

5. 路线 C：重建式 3D

这条路线常被忽略，但在实际工作中可能是性价比最高的——它的输入是真实世界。

分支 代表 输入 输出 特点
多视图重建 COLMAP 等传统 SfM/MVS 数十张照片 网格 + 纹理 成熟稳定，但慢，需要拍摄规范
高斯泼溅（3DGS） 3DGS 及其变体 视频/照片序列 高斯球（.ply） 渲染快、真实感强，但不是网格
前馈单图重建 Apple SHARP、SAM 3D Objects 单张图 高斯球/网格 + 位姿 秒级，零样本可用

两个近期值得关注的：

  • Apple SHARP：从单张照片生成可实时渲染的 3D 高斯表示，单次前馈推理，标准 GPU 上不到一秒；支持带绝对尺度的公制相机运动，可沿相机轨迹渲染视频。输出为遵循 OpenCV 坐标约定的 .ply。
  • SAM 3D Objects（Meta）：从单图 + 物体掩码重建完整几何、纹理与布局，能处理遮挡与杂乱场景，输出带位姿的模型与高斯球。

适用：已有实物的数字孪生（文物、场地、产品原型）、需要写实背景的场景板、参考素材采集、快速获取比例关系。

不适用：需要干净布线的可动资产、需要精确工程尺寸的零件、需要从零创造不存在的东西。

关键认知：3DGS 的输出是高斯球，不是网格。它渲染起来很快很真实，但要进游戏引擎当资产用，必须再做一次网格化——而网格化会损失细节。所以 3DGS 更适合背景、展示与参考，不适合当资产。

6. 路线 D：参数化 CAD 生成

这是最新、也最容易被技术美术忽略的一条线。它的差别在于：生成的不是几何，而是建模特征和约束。

目前有两种做法。

一是让 LLM 写 CAD 脚本，已经成熟。 CADQuery 是基于 OCCT 的 Python 参数化 CAD 框架（Apache 2.0），能直接输出 STEP / DXF / STL / 3MF / AMF / VRML。本质和路线 A 相同——AI 写代码、内核执行——但产物是工程级实体，尺寸精确。如果你需要的是「能拿去加工的零件」而不是「看起来像零件的模型」，这条路现在就能用，而且比生成式 3D 可靠得多。

二是端到端生成特征树，早期但方向明确。

  • Zoo（Text-to-CAD / Zookeeper）：用自然语言一次生成完全可编辑的 3D 模型，跑在自研几何引擎上，带检查、快照、调试几何的引擎级工具。
  • Backflip：三条输入路径——图纸转 CAD（识别工程图的几何与尺寸，重建为带完整特征树的可编辑模型）、扫描转 CAD（网格转参数化）、照片转 CAD（少量照片 + 一个已知尺寸做比例缩放）。它的关键主张是使用 Extrude、Revolve、Pattern、Chamfer、Fillet 这些真实建模操作，而不是生成「看起来像 CAD」的几何。产品形态是 Fusion 插件 + Web 应用。

这条线重要，是因为它是唯一一条**同时满足「AI 生成」和「可制造」**的路线。

维度 生成式 3D（路线 B） 参数化 CAD（路线 D）
输出本质 三角网格 B-Rep 实体 + 特征树
尺寸精度 不可靠 精确
改尺寸 需要重新生成 改一个参数即可
可制造性 需要修（打印修复、抽壳） 直接可加工
形面自由度 高（有机形状） 低（工程形状）
成熟度 生产可用（外观资产） 早期（特定品类）

结论很简单：有机形面走 B，工程实体走 D，不要拿 B 去做 D 的事。

8. 按任务反查：选型指南

这一节是给实际干活时用的。按任务找对应行，而不是按技术找场景。

你的任务 推荐 理由
主角角色、需要蒙皮动画 手工建模（AI 仅辅助概念） 四条路线都产出不了合格的可绑定拓扑
背景道具、场景填充 B + 轻量修 产能优势最大，质量要求可放宽
规则场景（街区、货架、室内布局） A 参数化是这类任务的天然解法
批量变体（一套模板出 N 个尺寸） A 或 D 代码或参数驱动，改数字重跑
管线杂活（重命名、UV、导出） A 性价比最高，风险最低
概念探索、快速预演 B 秒级出多方案，比手绘快

需要精确尺寸的零件 D 唯一输出 STEP 与特征树的路线
需要后期改尺寸的产品 D 改参数即可，不用重做
3D 打印 B（带修复）或 D B 需打印修复与抽壳，D 直接可切

一个实用的判断口诀：

需要「改」的 → A 或 D
需要「像」的 → B 或 C
需要「准」的 → D
需要「快」的 → B

9. 本地跑得动吗：16GB 显存的边界

以 RTX 5060 Ti 16GB 为参照（这是笔者的工作环境），按官方标注的显存下限逐条对照：

方案 官方显存需求 16GB 能否跑 说明
混元 3D 2.0（形状） 6GB 宽裕 门槛最低的起步方案
混元 3D 2.0（形状+纹理） 16GB 临界 需要关掉其他占显存的程序，实际可能 OOM
混元 3D 2.1（形状） 10GB 可以
混元 3D 2.1（纹理） 21GB 不行 只能跑形状阶段，纹理需上云或退回 2.0
TRELLIS（1.2B–2B） ≥16GB 临界 官方验证环境是 A100/A6000，消费卡有风险
TRELLIS.2（4B） ≥24GB 不行 需 3090/4090 或云端
TripoSG（1.5B） 未公开 大概率可以 参数量小，需自行验证
UniRig（自动绑定） 8GB 可以 骨架生成 + 蒙皮权重，MIT 许可
SHARP（单图重建） 未公开 大概率可以 模型轻，秒级推理
bpy 脚本路线 不占显存 完全没问题 这是零门槛优势

几条实践建议：

  1. 16GB 的现实定位是「形状生成 + 轻量材质」，完整 PBR 纹理管线基本要上云。如果材质是硬需求，直接考虑商用 API 更省事。
  2. ComfyUI 生态里已经有混元 3D 等模型的集成。 如果本来就在用 ComfyUI 做工作流，这条路能省掉不少环境配置的麻烦——但显存是共享的，不能和图生图、视频模型同时跑。
  3. 别忽略 UniRig 这类下游模型。 它不生成模型，但能自动出骨架和蒙皮权重（Rig-XL 数据集含 14000+ 已绑定模型），8GB 就能跑。对于「生成出来的模型怎么变成可动资产」这个问题，它比再换一个生成模型有用得多。

10. 陷阱清单与验收标准

六个常见陷阱：

  1. 拿生成式结果当成品交付。 布线、UV、尺度都不可控，进引擎就是灾难。验收要以「能否二次编辑」为准，不是「看起来像不像」。
  2. 指望 AI 做审美判断。 路线 A 能算比例，算不了好看。所有形面微调的活仍然要人。
  3. 忽略版本漂移。 Blender 一年两个大版本，bpy API 会变。锁定 LTS、把脚本写短。
  4. 用三角面汤做动画。 没有语义部件就没有蒙皮，没有蒙皮就没有动画。需要动，先分割。
  5. 把 3DGS 当资产。 高斯球渲染快，但它不是网格。
  6. 忽略许可。 各仓库许可不同（TRELLIS 与 TRELLIS.2 是 MIT，部分子模块另有条款；商用平台的水印与商用授权需按套餐确认）。商用前逐条读，不要默认「开源的就能商用」。

针对生成式产出，至少过这五关：

关卡 检查什么 不过怎么办
1 几何 有没有破面、翻转法线、非流形边 修，或重新生成
2 拓扑 布线是否连续、面数是否可控 重拓扑，或改用带四边面输出的方案
3 UV 是否规整、有无拉伸 重展 UV
4 材质 PBR 通道是否完整（albedo/normal/roughness/metallic） 补 AI 贴图或手绘
5 尺度 单位是否正确、比例是否合理 按参考物标定

建议把这张表变成脚本，对批量产出自动跑一遍第 1、2、5 三项——这三项最容易出问题，也最容易自动化。

总结

AI 现在能做的是「把结构变成资产」，还做不了「把审美变成资产」。

判断一个任务该不该交给 AI，就问一句：这个任务的成败，取决于规则，还是取决于手感？取决于规则的交出去，取决于手感的手工做。 这也是当前阶段四条路线各自成立的原因——它们各自覆盖了一部分「规则」，而没有任何一条覆盖「手感」。

具体到落地，我自己的默认姿势是 A + B 组合：用脚本管批量、管规则、管杂活，用生成模型出形面和贴图，最后人工做重拓扑与绑定。凡是有人兜底的那一段，可以放心交给 AI；凡是没人兜底、要直接交付的那一段，仍然得自己上手。
